## 1. 장비 45 → 44 감소 원인 추적

### 1-1. 사라진 공고 특정

커밋별로 공고 집합을 훑어 시간 순서로 추적했다.

| 커밋 | 시각(UTC) | 총건수 | 장비 | 변화 |
|---|---|---|---|---|
| `c16fce0` | 09-03 23:54 | 67 | 45 | — |
| **`917172a`** | **09-04 00:28** | **65** | **43** | **-2** |
| `630be47` | 09-04 00:32 | 66 | 44 | +1 (JETRO 수동 복원) |
| `5bfc7a3` | 09-04 01:54 | 66 | 44 | — |

`917172a`는 **No.014의 Actions 1차(run 33821253819)** 결과다. 여기서 2건이
동시에 빠졌다.

| ID | 출처 | 판정 | 제목 | 처리 |
|---|---|---|---|---|
| `jetro401416` | JETRO | 장비 | 고속 스캐닝 전자빔 리소그래피 장비 1식 | No.014에서 복원(상세 503) |
| **`ebnew709582888`** | **EBNEW** | **장비** | **반도체 장비 2차 국제 입찰공고 (1)** | **미복원 → 45→44의 원인** |

### 1-3. 원인 판정 — 지시문 3번 분류

근거를 단계별로 확인했다.

1. **원본이 살아 있는가?** 상세 페이지를 직접 열었다. 제목이 그대로 있고
   `投标截止时间（开标时间）: 2026-09-11 10:00`으로 마감도 남아 있다.
   → **삭제 아님.**
2. **상세 요청이 실패했는가?** No.014 1차 로그에 `709582888` 문자열 자체가
   없다. 상세 단계까지 가지도 못했다. → **상세 실패 아님.**
3. **목록 수집이 실패했는가?** EBNEW는 정상 수집됐다(raw 35건, 최종 19건).
   → **목록 실패 아님.**
4. **지금 검색 결과에 있는가?** `半导体设备` 검색 **2페이지 2번째**에 있다.
   수집 범위(1~2페이지) 안이다.
5. **그럼 왜 빠졌나?** `LOOKBACK_DAYS = 14` 조회 창이다.
   ```python
   cutoff = (오늘 - 14일).isoformat()
   if row["date"] and row["date"] < cutoff:
       stop_keyword = True
       break
   ```
   게시일이 **2026-08-20**이라
   - 09-03 실행: 컷오프 `2026-08-20` → `"2026-08-20" < "2026-08-20"` 은 거짓 → 포함
   - 09-04 실행: 컷오프 `2026-08-21` → 참 → **제외**

**결론: 지시문 3번의 A~G 어디에도 정확히 맞지 않는 H(기타)다.**

> **45→44 감소 원인: EBNEW 수집기의 14일 조회 창(LOOKBACK_DAYS)을 게시일이
> 벗어나 제외된 것. 원본 공고는 삭제되지 않았고 마감(2026-09-11)도 남아 있다.**

원본 삭제가 아니므로 지시문 4번의 "억지 복원 금지"에 해당하지 않고,
시스템 쪽 누락이므로 5번대로 복원 대상이다.

### 1-4. 조치

**규칙 수정** — 게시일이 오래됐다고 끝난 공고는 아니다. 마감일이 남아
있으면 지금도 응찰 가능하므로 조회 창 밖이라는 이유만으로 버리지 않는다.

```python
if row["date"] and row["date"] < cutoff:
    stop_keyword = True            # 다음 페이지는 보지 않는다(최신순이라)
    if not is_still_open(row):     # 마감 전이면 이 건은 살린다
        break
```

마감일을 못 읽으면 `is_still_open`이 False를 돌려준다 — 확실하지 않은 것을
붙들어 오래된 공고가 무한정 쌓이지 않게 한다.

**영향 범위 실측** — 현재 검색 결과 전수를 확인했다.

| 구분 | 건수 |
|---|---|
| 조회 창 밖 + 관련 공고 | 14건 |
| 그중 **아직 마감 전**(살아나는 것) | **2건** |
| 그중 이미 마감(영향 없음) | 12건 |

늘어나는 것은 2건뿐이다 — 잃어버린 `ebnew709582888`과, 계속 놓치고 있던
`ebnew709541568`(게시 08-17, 마감 09-09).

**데이터 복원** — 잃어버린 1건을 원래 `firstSeenAt`
(`2026-08-20T22:21:07+00:00`) 그대로 되살렸다. 그래야 다음 실행에서 신규로
오인되어 Telegram이 다시 나가지 않는다.

## 2. 6개 수집기 상세실패 구조 감사

### 2-1. 감사 전 구조

| 수집기 | 목록 | 안정 ID | 상세 요청 | 상세 실패 시 | 위험 |
|---|---|---|---|---|---|
| KANC | 게시판 HTML | `cid{cid}` | 있음 | `continue` → 소실 | **있음** |
| NNFC | 게시판 HTML | `nttid{ntt_id}` | 있음 | `continue` → 소실 | **있음** |
| KRISS | 게시판 HTML | `kriss{list_no}` | 있음 | `continue` → 소실 | **있음** |
| KOTRA | AJAX 카드 | `kotra{biz_no}` | 있음 | `continue` → 소실 | **있음** |
| EBNEW | 검색 HTML | `ebnew{url의 숫자}` | 있음 | `build_item`이 `None` → 소실 | **있음** |
| MOFCOM | 검색 JSON | `mofcom{fdid}` | 있음 | `build_item`이 `None` → 소실 | **있음** |
| JETRO | 목록 JSON | `jetro{xid}` | 있음 | 기존 공고 유지 | 없음(No.015) |
| DGIST | 게시판 HTML | `no` | 있음 | 목록 정보로 구성 | 없음 |
| ITRI · KAIST | 목록만 | — | **없음** | 해당 없음 | 없음 |

EBNEW·MOFCOM은 다른 6곳과 구조가 달랐다. 상세 실패가 `None`으로 돌아와
**"장비 공고가 아니라 걸러냈다"(정상)와 구분되지 않았다.** 그래서 일시
장애로 빠진 공고가 정상 제외와 똑같이 취급됐다.

### 2-2. 공통 도구 (지시문 20번)

6곳이 같은 형태라 `collectors/common.py`에 공용으로 뒀다.

```python
class DetailFetchFailed(RuntimeError): ...      # '장비 아님'과 구분하는 신호
def previous_index(previous_items): ...          # 직전 결과 id 조회용
def keep_or_defer(prev_index, item_id, tag, exc)  # 유지 or 보류 + 로그
```

`fetch_announcements.run_collector`가 `PREVIOUS_ITEMS`를 선언한 수집기에만
직전 결과를 넘긴다. 선언하지 않은 수집기(DGIST·ITRI·KAIST)의 동작은 그대로다.

### 2-3. 수집기별 적용

| 수집기 | 수정 방식 | 결과 |
|---|---|---|
| KANC | `except` 블록 교체 | 기존 공고 유지 |
| NNFC | `except` 블록 교체 | 기존 공고 유지 |
| KRISS | `except` 블록 교체 | 기존 공고 유지 |
| KOTRA | `except` 블록 교체 | 기존 공고 유지 |
| EBNEW | `None` → `DetailFetchFailed` 예외 + 호출부에서 구분 | 기존 공고 유지 |
| MOFCOM | 〃 | 기존 공고 유지 |

KANC·NNFC·KRISS·KOTRA는 구조가 같아 `except` 블록만 바꾸면 됐다.
장비 필터·판정 규칙은 어느 수집기도 건드리지 않았다(지시문 14~19번).

### 2-4. 세 경우를 분리했는가 (지시문 11번)

| CASE | 상황 | 처리 |
|---|---|---|
| A | 목록 전체 실패 | 수집기가 예외 → `run_collector`가 기존 데이터 유지 + Health 실패 |
| B | 목록 정상 + 기존 ID + 상세만 실패 | **해당 공고만 기존 데이터 유지**, source는 정상 |
| C | 목록 정상 + 해당 ID 없음 | 유지하지 않음 → 기존 종료/삭제 정책대로 |

C가 그대로 남아 있으므로 "상세 실패 보존"이 "영구 보존"으로 바뀌지 않는다
(지시문 21번).

### 2-5. 신규 ID + 상세 실패 (지시문 13번)

유지할 기존 데이터가 없다. 목록 정보만으로 상세를 지어내지 않고 **다음
실행으로 미룬다**. 로그에 `신규라 보류 N건`으로 남는다.

DGIST 방식(목록 정보로 구성)도 가능하지만, 상세에만 있는 마감일·첨부·규격이
빠진 채 항목이 만들어져 Telegram 추천까지 나갈 수 있어 택하지 않았다.

### 2-6. 상세 stale 로그 (지시문 26번)

```
[EBNEW] 상세 요청 실패 — 목록에는 있으므로 기존 공고 유지: ebnew709582888 (...)
[EBNEW] 상세 요청 실패 — 기존 데이터가 없는 신규 공고라 이번 실행에서는 보류: ... 
[EBNEW] 상세 요청 실패 처리: 기존 공고 유지 1건 / 신규라 보류 0건
```

출처·공고 ID·실패 사실·유지 여부가 모두 식별된다.

## 3. 사용자 화면 외국어 최종 재감사

### 3-1. No.015 보고의 표현 정리 (지시문 31번)

No.015 보고에 "한자·가나 0건"과 "잔여: 大台/奕斯伟/奕成/电子"가 함께 있어
모순처럼 보였다. 실제로는 모순이 아니라 **표기 방식의 문제**였다.

한자 원문은 `original*` 필드에만 있고(정상), 사용자 화면에는 그 **로마자
표기**가 보인다. 보고서가 잔여를 한자로 적어 마치 한자가 화면에 있는 것처럼
읽혔다.

### 3-2. 유형별 분리 (지시문 32번)

| 표현 | 사용자 필드 한자 | 원문 필드 한자 | 화면 로마자 | 유형 |
|---|---|---|---|---|
| 大台 | 0건 | 2건 | `DaTai` | **C** |
| 奕斯伟 | 0건 | 1건 | `YiSi Wei` | **C** |
| 奕成 | 0건 | 1건 | `YiCheng` | **C** |
| 电子 | 0건 | 8건 | `DianZi` | **C** |

한자 자체는 모두 **유형 A(원문 필드에만 존재 — 정상)**이고, 화면에 보이는
것은 로마자 4종이다.

### 3-3. 처리 결과

| 표현 | 조치 | 근거 |
|---|---|---|
| `电子` | **전자** | 일반 기술용어. 회사명 접미사("…电子有限公司")로 흔히 쓰인다. `电子材料`·`微电子`·`光电子`를 함께 넣어 긴 조합어가 먼저 치환되게 했다 |
| `奕斯伟` | **이쓰웨이(ESWIN)** | 회사 자체 도메인 `eswin.com`에서 "北京奕斯伟科技集团有限公司-官网" 확인. 한국어는 발음 음역이며 사전의 다른 회사와 같은 방식 |
| `奕成` | **이청** | 공식 영문명 미확인 → 음역만 사용 |
| `大台` | **그대로 유지** | 공개 원문(EBNEW 상세)에도 설명이 없다. 뜻을 지어내지 않는다. 번역 미완료 배지와 원문 링크로 안내된다 |

`维信诺` 표기도 `Visionox(웨이신눠)` → `웨이신눠(Visionox)`로 뒤집어
한국어를 앞세우는 No.015 원칙에 맞췄다.

### 3-4. `大台`를 안전 문구로 바꾸지 않은 이유 (지시문 34번)

`"원문 표현 확인 필요"` 같은 표시로 대체하는 방안을 검토했으나 택하지
않았다. 현재 표시는 `DaTai 레이저 현미경`으로, **장비 종류(레이저 현미경)는
읽힌다.** 이를 안내 문구로 바꾸면 정보가 오히려 줄어든다. 번역이 불완전하다는
사실은 이미 `번역 미완료` 배지로 알리고 있고 원문 링크도 있다.
