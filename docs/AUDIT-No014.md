# 장비 False Negative 안전망 감사 — 지시문 No.014 12~24번

No.013에서 "산업 근거 없음 + 장비 신호 있음 → 제외"로 일반화했다. 현재 67건
에서는 KRISS 1건만 바뀌었지만, 미래 데이터에서 실제 장비를 놓칠 위험이
있는지 감사한다.

---

## 1. 감사 방법

지시문 14번이 나열한 "강한 장비 신호" 33종을 산업 단어 없이 그대로 넣고
현재 규칙이 어떻게 판정하는지 실측했다.

## 2. 결과 — 12종이 자동 제외되고 있었다

| 입력 | No.013 판정 | 원인 |
|---|---|---|
| `stepper` / `스테퍼` | 제외 | `PROCESS_INDUSTRY_TERMS`에 노광 계열은 있으나 stepper는 없음 |
| `etcher` | 제외 | `etch`는 있지만 영문은 단어 경계로 맞춰 `etcher`에 걸리지 않음 |
| `tester` / `시험기` | 제외 | KANC·NNFC 출처일 때만 인정되던 신호 |
| `plating system` / `도금 장비` | 제외 | 도금 계열이 산업 신호 목록에 없음 |
| `inspection system` / `검사 장비` | 제외 | AOI만 있고 일반 inspection은 없음 |
| `metrology system` / `계측 장비` | 제외 | 계측 계열이 산업 신호 목록에 없음 |
| `plasma processing system` / `플라즈마 처리 장비` | 제외 | 플라즈마는 KANC·NNFC 전용 신호였음 |
| `본더` | 제외 | `bonding`은 있으나 한글 `본더` 단독은 없음 |

나머지 21종(prober, AOI, CMP, MOCVD, ALD/CVD/PVD, sputtering, wet bench,
furnace, RTP, lithography, 노광기, 식각기, 성장로 등)은 이미 산업 신호로도
잡혀 정상적으로 `장비` 판정된다.

**즉 "산업 근거 없음"이 곧 "산업 무관"으로 처리되고 있었다.** 상세 페이지를
못 읽었거나 제목이 짧아 산업 단어가 안 보이는 경우까지 같이 버렸다.

## 3. 새 안전망

지시문 17번의 5단계를 그대로 구현했다. `equipment_filter.classify()` 순서:

```
1. 시설·유틸리티 신호        → 제외   (FACILITY_TERMS)
2. 산업이 명백히 다른 분야    → 제외   (UNRELATED_INDUSTRY_TERMS)  ← 신설
3. 장비 구매가 아님이 분명    → 제외   (STRONG_NON_EQUIPMENT_TERMS)
4. 산업 확실 + 장비 확실     → 장비
5. 산업 없음 + 팹 공정 장비명 → 검토   (STRONG_EQUIPMENT_TERMS)    ← 신설
6. 산업 없음 + 일반 장비어    → 제외
7. 산업 없음 + 장비도 아님    → 제외
```

**2번(UNRELATED)이 5번보다 앞이다.** 장비처럼 보인다는 이유로 의료기기나
항공관제 시스템을 반도체 장비로 올리지 않기 위해서다.

### "모른다"와 "아니다"의 구분 (지시문 16번)

| 상황 | 판정 | 이유 |
|---|---|---|
| 의료용 검출기, 항공관제 시스템 | **제외** | 산업이 다른 분야임이 **확인됨** |
| `Plasma Processing System`, 상세 수집 실패 | **검토** | 산업 정보를 **아직 못 읽음** |
| `중적외선 레이저 시스템`(KRISS) | **제외** | 공개 규격서로 용도 확인 완료 — 정보 부족이 아님 |
| 일반 측정기·레이저·현미경 | **제외** | 팹 공정 장비를 특정하지 않음 |

### 검토를 늘리지 않기 위한 선 (지시문 18번)

`STRONG_EQUIPMENT_TERMS`에는 **팹 공정 장비를 특정하는 이름만** 넣었다.
`장비`·`설비`·`시스템`·`측정기`·`레이저`·`현미경` 같은 일반어는 넣지 않았다.
넣으면 일반 연구장비가 전부 검토로 쏟아져 검토 목록이 무의미해진다.

이 선 덕분에 KRISS 중적외선 레이저 시스템은 안전망에 걸리지 않고 제외를
유지한다(지시문 19번 요구사항).

## 6. 작업 중 잡은 자체 결함

`UNRELATED_INDUSTRY_TERMS`에 `"수의"`(수의학)를 넣었더니 정부 계약방식인
**`"소액수의계약"`·`"특정수의계약"`**에 걸려 멀쩡한 KANC 공고 3건이
"수의학 분야"로 분류됐다. 판정(제외)은 그대로여서 판정만 비교했을 때는
드러나지 않았고, **사유까지 비교해서야** 발견했다.

한글은 부분 문자열로 맞추므로 짧은 단어를 넣으면 안 된다. 같은 이유로
`"제약"`(→ 설계 제약), `"사료"`(→ 검사료), `"조리"`(→ 조리개)도 뺐다.
이후로는 판정과 **사유를 함께** 비교한다. 회귀테스트에도 고정했다.

(No.013의 `"모니터"` → `"모니터링"` 오제외와 같은 유형이다. 한글 용어를
목록에 넣을 때 반복되는 함정이므로 코드 주석에 남겼다.)

## 7. 수집 실패와 판정 실패의 연결 (지시문 24번)

**판정 쪽은 안전하다.** 상세를 못 읽어 산업 근거가 사라져도, 제목에 팹 공정
장비 이름이 있으면 3절의 5번 분기가 검토로 잡는다. 자동 제외로 내려가지
않는다. 회귀테스트 `test_missing_detail_does_not_force_exclude`로 고정했다.

**다만 판정 이전 단계에 더 큰 문제가 있다.** 1차 실행에서 실제로 발생했다.

JETRO 상세 페이지 하나가 `HTTP 503`을 냈고, 재시도(2회)를 다 쓴 뒤 그 공고가
**결과에서 통째로 빠졌다**("고속 스캐닝 전자빔 리소그래피 장비 1식").
JETRO는 매 실행 결과로 목록을 갈아끼우므로 공고가 데이터에서 사라진다.
그러면 `firstSeenAt`도 함께 사라지고, `notify_telegram`은 직전 스냅샷만
비교하므로 **다음 실행에 그 공고가 돌아오면 "신규 공고"로 다시 알림이 나간다.**

즉 판정 이전에 데이터가 없어지므로 안전망이 작동할 기회조차 없다.

이번에 한 조치:

- 상세 요청 시도 횟수를 목록과 같은 3회로 맞춰 일시적 5xx로 공고를 잃는
  빈도를 줄였다.
- 실패 로그에 "다음 실행에 돌아오면 신규로 인식된다"를 명시했다.
- 빠진 공고 1건을 원래 `firstSeenAt` 그대로 복원해 재발송을 막았다.

**근본 해결은 아니다.** 재시도를 늘려도 상세가 계속 실패하면 같은 일이
생긴다. 구조적으로는 "상세를 못 읽은 공고를 목록 정보만으로라도 남기고
`detailFetchFailed` 표시를 붙여 검토로 보내는" 방식이 맞다. 다만 이는
데이터에 무엇을 담을지에 대한 판단이 필요하고 지시문 24번도 "검토한다"로
두었으므로, 이번에는 구현하지 않고 사용자 판단 항목으로 남긴다.
