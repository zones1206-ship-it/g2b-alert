## 4. 자동 검사의 판정 기준

수집을 막을 만한 것과 사람이 판단할 것을 구분한다.

**치명(exit 1)** — 사용자 필드의 한자·가나, 금지된 영어 UI 문구.
번역 경로가 무조건 로마자로라도 바꾸게 되어 있으므로, 여기 걸리면
파이프라인이 깨진 것이다.

**경고(exit 0)** — 로마자 폴백, 허용 목록 밖 영단어.
공고 원문에 원래 영어 모델명이 들어 있는 경우가 많다(예: KANC의
`AIT-XP … Solid State Laser`, `Large-area Metal-Organic Chemical Vapor
Deposition 1SET`). 이것만으로 수집을 막으면 정상 공고가 들어오지 못한다.

회귀테스트는 치명 항목만 고정하고, 경고는 사람이 보도록 남긴다.

## 5. 상세 요청 실패 시 공고 소실 위험 — 나머지 9개 수집기 감사

질문: **"목록은 성공했는데 상세 한 건이 실패하면 기존 공고가 데이터에서
사라지는가?"**

| 수집기 | 상세 요청 | 실패 시 동작 | 위험 |
|---|---|---|---|
| **JETRO** | 있음 | **기존 수집분 유지** (이번에 수정) | **해소** |
| **DGIST** | 있음 | 목록 정보만으로 항목을 구성 | **없음** |
| KANC | 있음 | `건너뜀` → 공고 소실 | **있음** |
| NNFC | 있음 | `건너뜀` → 공고 소실 | **있음** |
| KRISS | 있음 | `건너뜀` → 공고 소실 | **있음** |
| KOTRA | 있음 | `건너뜀` → 공고 소실 | **있음** |
| EBNEW | 있음 | `건너뜀` → 공고 소실 | **있음** |
| MOFCOM | 있음 | `건너뜀` → 공고 소실 | **있음** |
| ITRI | 없음(목록만) | 해당 없음 | 없음 |
| KAIST | 없음(목록만) | 해당 없음 | 없음 |

**같은 위험이 6곳에 남아 있다.**

소실되면 `firstSeenAt`이 함께 사라져 다음 실행에 그 공고가 신규로 오인되고
Telegram이 다시 나간다. JETRO에서 실제로 발생한 것과 같은 구조다.

이번에 함께 고치지 않은 이유는 1~2줄로 끝나는 수정이 아니기 때문이다.
수집기마다 ID 만드는 방식과 `build_item` 인자가 달라, JETRO에 적용한 방식
(`PREVIOUS_ITEMS` 선언 → 직전 결과 조회 → 실패 시 기존 항목 재사용)을
그대로 옮기려면 수집기당 5~8줄 수정과 각각의 검증이 필요하다. 지시문
28번이 "대규모 수정이 필요하면 다음 작업 후보로 보고한다"고 정한 범위에
해당한다.

**권장 처리 순서** — 실패 빈도와 영향이 큰 순:

1. **EBNEW · MOFCOM** — 검색형이라 상세 요청이 가장 많고, 중국 사이트라
   타임아웃·차단이 잦다.
2. **KOTRA** — 러너 IP에 따라 상세 요청이 자주 끊긴다(선택적 차단).
3. **KANC · NNFC · KRISS** — 국내 게시판이라 실패가 드물지만 구조는 같다.

DGIST 방식(목록 정보만으로 항목 구성)도 대안이지만, 상세에만 있는 마감일·
첨부·규격이 빠진 채로 항목이 만들어지므로 JETRO 방식(기존 데이터 재사용)이
더 안전하다. 신규 공고라 기존 데이터가 없는 경우에만 DGIST 방식을 쓰거나
다음 실행으로 미루는 것이 좋다.
