# 10개 수집기 수집 범위 전수 감사 — 지시문 No.017

핵심 질문: **"상세 요청 실패가 아니더라도, 진행 중 공고가 수집 범위 밖으로
밀리면 데이터에서 사라질 수 있는가?"**

답: **그렇다.** 실제로 두 번 발생했다(EBNEW·KAIST).

## 3. KAIST 원인 확정과 해결 (지시문 7~11번)

### 3-1. 누락 공고

| 항목 | 값 |
|---|---|
| ID | `kaistR26BK01704393` |
| 제목 | 반도체 웨이퍼 노광장비 구매_260270 |
| 마감일 | **2026-09-08** (누락 시점 기준 나흘 뒤) |
| firstSeenAt | 2026-09-03T11:03:49+09:00 |
| 원본 URL | 나라장터 `bidPbancNo=R26BK01704393` |
| 원본 생존 | **살아 있음** — 게시판 목록에 그대로 있다 |
| 현재 위치 | **2페이지 1번째** |

### 3-2. 페이지네이션 조사 결과

No.016에서는 "페이징 파라미터가 없어 1~2줄로 고칠 수 없다"고 결론냈다.
**그 결론은 틀렸다.** 상수(`LIST_URL = SOURCE_SITE_URL`)만 보고 실제 페이지
HTML을 열어보지 않았다.

페이지 HTML의 페이지네이션 블록에 평범한 GET 링크가 있다.

```html
<ul class='pagination pg-blue'>
  <li><a class='page-link' href='?site_dvs_cd=kr&menu_dvs_cd=0815&skey=&sval=&&GotoPage=2'>2</a></li>
  ...
  <li><a class='page-link' href='?...&GotoPage=10' aria-label='last'>»</a></li>
</ul>
```

| 확인 항목 | 결과 |
|---|---|
| HTML 페이지 링크 | **있음** (`GotoPage=N`) |
| form submit / hidden input | 목록과 무관(사이트 검색 폼) |
| javascript onclick | 목록과 무관(사이트 메뉴 `pageMove`) |
| POST / AJAX | 불필요 |
| 로그인 | 불필요 |
| 총 페이지 | 10 |
| 정렬 | 게시일 최신순 |

실제로 `GotoPage=2`를 요청해 10건이 정상 파싱되고 누락 공고가 1번째에
있는 것을 확인했다.

### 3-3. 적용한 해결

3페이지(30건)를 읽는다. 게시 빈도(하루 1~3건)를 보면 마감 전 공고를 넉넉히
덮으면서 과거 공고를 무제한으로 긁지는 않는다. 페이지 파라미터가 안 먹어
같은 내용이 반복되면 그만 읽는다.

실측: raw 10건 → **30건**, 최종 1건 → **3건**(노광장비 포함).

## 4. 공통 Active Notice 보존 원칙 (지시문 5·22~25번)

수집기별 창 구조가 제각각이라 **orchestrator 한 곳**에서 처리한다.
`fetch_announcements.preserve_active_missing_items()`.

동작 조건 — 셋 다 만족해야 되살린다.

1. 목록 수집이 **정상**이었다 (실패면 `run_collector`가 이미 전체 유지)
2. 직전 실행에 있던 공고가 이번 결과에 없다
3. **마감일이 아직 남아 있다** + **취소·폐기 표기가 없다**

| 상황 | 처리 | 근거 |
|---|---|---|
| 마감 전 + 목록 밖 | **유지** | 범위 이탈 가능성(지시문 5·6 CASE B/C) |
| 마감 지남 + 목록 밖 | 제거 | 영구 보존 금지(지시문 25) |
| 취소·폐기 표기 | 제거 | 지시문 24 |
| 마감일 없음 | 제거 | 무한 누적 방지(지시문 4) |
| 목록 전체 실패 | 건드리지 않음 | 기존 source stale 정책(지시문 11 CASE A) |

마감일이 지나면 자동으로 빠지므로 **"상세 실패 보존"과 "영구 보존"이
구분된다**(지시문 21).

되살릴 때 **기존 item 객체를 그대로** 넘긴다. 따라서 id·firstSeenAt·title·
org·equipmentStatus·equipmentReason·dueDate·originalUrl이 모두 유지되고,
`stamp_first_seen`도 기존 값을 그대로 둔다(지시문 12·27).

## 5. 단순 dueDate 보존의 위험 (지시문 23번)

"마감 전이면 무조건 유지"만 하면 취소된 공고가 마감일까지 남는다.
그래서 취소·폐기 표기(`취소`/`폐기`/`철회`/`무효`/`재공고로 대체`)를
`status`·`title`·`originalTitle`·`noticeType`에서 확인해 제외한다.
기존 status 체계를 쓰며 새 상태머신은 만들지 않았다.

원본 URL 404 확인까지는 하지 않는다 — 보존 대상 전건에 대해 매 실행마다
원본을 찌르면 요청이 늘고, 마감일 상한이 이미 있어 무한 보존은 불가능하다.

## 6. 마감일 없는 공고 (지시문 4번)

현재 데이터 70건 중 **32건(46%)에 `dueDate`가 없다.**

| 출처 | 마감일 없음 | 수집 범위 여유 |
|---|---|---|
| JETRO | 19 | 넉넉(120일 × 840건) |
| EBNEW | 7 | 넉넉(검색 14키워드 × 2페이지) |
| KANC | 5 | 넉넉(30일 × 100건) |
| KOTRA | 1 | 넉넉(240건) |

이들은 보존 대상에서 빠지지만, **전부 수집 범위가 넉넉한 출처**라 실제
위험은 낮다. 마감일 없는 공고의 lifecycle 정책(postedDate·firstSeenAt·
게시판 보존기간 기반)은 이번 작업 범위를 넘어서므로 만들지 않았고
보고 대상으로 남긴다.

## 7. 되살린 공고가 신규로 보이지 않게 (지시문 27~29번)

- 기존 item 객체를 그대로 넘겨 **id·firstSeenAt 유지**
- `notify_telegram`은 직전 스냅샷과 비교하는데, 보존분은 스냅샷에도
  그대로 있으므로 신규로 잡히지 않는다
- NEW 배지는 `firstSeenAt` 기준 48시간이라 재생성되지 않는다
- 실제 신규 공고는 보존 로직을 타지 않으므로 정상 알림된다(지시문 29)
